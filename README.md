# crow-backend

Django REST Framework backend for tracking card payment expenses. Receives card payment SMS notifications via webhook, parses them, and syncs with Notion databases.

[![CI](https://github.com/nonasking/crow-backend/actions/workflows/ci.yml/badge.svg?branch=develop)](https://github.com/nonasking/crow-backend/actions/workflows/ci.yml)
[![codecov](https://codecov.io/gh/nonasking/crow-backend/branch/develop/graph/badge.svg)](https://codecov.io/gh/nonasking/crow-backend)
[![Python](https://img.shields.io/badge/python-3.13%2B-3776AB?logo=python&logoColor=white)](https://www.python.org/)
[![Django](https://img.shields.io/badge/django-6.0-092E20?logo=django&logoColor=white)](https://www.djangoproject.com/)

- **Production** — running on Render for 3+ months. Card payment SMS → real-time parsing → PostgreSQL → Notion sync, used daily.
- **Testing** — 134 tests across 14 modules. pytest-django integration tests with JWT-authenticated fixtures and external API mocking.
- **Merchant normalization** — SMS item strings (`(일시불)06/20 카페63도`) are normalized to clean merchant names, with a reversible data migration and original-value backups.
- **Auto-classification** — deterministic rules learned from manually-confirmed history fill in `UNSETTLED` expenses. Dry-run by default, and never learns from its own output.
- **API docs** — OpenAPI 3 schema auto-generated by drf-spectacular (Swagger UI / ReDoc).

## Architecture

```mermaid
flowchart TB
    SMS[Card payment SMS] --> FWD[SMS forwarder app]
    FE["crow-frontend<br/>(web client)"]

    subgraph backend["crow-backend (Django + DRF)"]
        direction TB

        subgraph rcv["receivers"]
            WH["SMSReceiverView<br/>POST /receivers/webhook/"]
            PARSE["ParseSMSService<br/>Shinhan / Woori dispatch"]
            NORM["normalize_merchant<br/>(single source of truth)"]
            REC["card_payment_service<br/>MM/DD → date (KST) · Notion + Expense"]
            NC["NotionClient"]
            WH --> PARSE --> NORM
            WH --> REC --> NC
        end

        subgraph auth["authentication"]
            JWT["JWT login / logout / me<br/>POST /auth/*"]
        end

        subgraph exp["expenses"]
            API["ExpenseViewSet / BudgetViewSet<br/>CRUD · filters · summary"]
            BSVC["BudgetService<br/>duplicate guard"]
            SUM["expense_summary_service<br/>totals · prorated budget"]
            ACSVC["auto_classify_service<br/>learn rules → classify UNSETTLED"]
            CMD["manage.py commands<br/>auto_classify_unsettled<br/>preview_item_cleanup"]
            API --> BSVC
            API --> SUM
            CMD --> ACSVC
        end

        MODELS[["Models<br/>Expense · Budget · ExpenseItemBackup"]]
    end

    FWD -- "POST {message}" --> WH
    FE -- "Bearer JWT" --> API
    JWT -. authenticates .-> API

    REC --> MODELS
    NC <-. "import / sync" .-> NOTION[(Notion DB)]
    API --> MODELS
    ACSVC -- "reads history,<br/>writes UNSETTLED only" --> MODELS
    MODELS --> PG[(PostgreSQL)]
```

Three apps split by responsibility, plus one stub:

- `receivers` — webhook endpoint, SMS parsing (`ParseSMSService`), merchant normalization (`normalize_merchant`), payment recording (`card_payment_service`), and the Notion API client.
- `expenses` — Expense / Budget CRUD, summary aggregations, Notion import, and the auto-classification service behind its management command.
- `authentication` — JWT login / logout / current user; backs the auth fixture used in the rest of the test suite.
- `analytics` — scaffolded, not implemented. No models, views, or routes yet.

External clients hit DRF endpoints; the service layer owns parsing, aggregation, classification, and Notion sync. Single-field validation lives in serializers. ViewSets stay thin.

`normalize_merchant` lives in `receivers.services` and is reused verbatim by the expenses data migration and the auto-classifier — the parser and the classifier must agree on what a merchant name *is*, so there is exactly one implementation of it.

## Setup

### Prerequisites

- Python 3.13+
- PostgreSQL
- [Poetry](https://python-poetry.org/docs/#installation)

### 1. Install dependencies

```bash
poetry install
```

### 2. Configure environment

Create `.env.local` in the project root:

```env
SECRET_KEY=your-secret-key
DEBUG=True

DATABASE_URL=postgres://user:password@localhost:5432/crow

NOTION_TOKEN=your-notion-integration-token
NOTION_EXPENSE_DATABASE_ID=your-expense-db-id
NOTION_BUDGET_DATABASE_ID=your-budget-db-id
NOTION_VERSION=2022-06-28
```

> The app reads `.env.{DJANGO_ENV}` where `DJANGO_ENV` defaults to `local`.
> For production, set `DJANGO_ENV=production` and create `.env.production`.

### 3. Apply migrations

```bash
poetry run python manage.py migrate
```

### 4. Create a superuser

```bash
poetry run python manage.py createsuperuser
```

### 5. Run the development server

```bash
poetry run python manage.py runserver
```

### SMS Receiver

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| `POST` | `/receivers/webhook/` | None | Receive card payment SMS and sync to Notion |

Supports **Shinhan** and **Woori** card SMS formats. The service parses the raw SMS text into structured data (`amount`, `item`, `payment_method`, `spent_at`), writes it to Notion, and saves it as an `UNSETTLED` expense.

The SMS only carries `MM/DD`, so the year is inferred: this year, unless that lands in the future, in which case last year. "Today" is taken in KST (`expenses.constants.LOCAL_TIMEZONE`), not the server's UTC, so payments made between 00:00 and 08:59 KST don't get pushed back a year.

**Request:**
```json
{ "message": "[Web발신]\n신한카드(1234)승인 2,400원 04/20 14:32 세븐일레븐" }
```

## Merchant Normalization

Card SMS puts the payment marker and date in front of the merchant name, so the raw item reads `(일시불)06/20 카페63도` rather than `카페63도`. `normalize_merchant` (in `receivers.services`) strips the `(일시불)` / `(할부N개월)` marker, the leading `MM/DD` date and optional `HH:MM` time, and corporate forms (`(주)`, `주식회사`, `㈜`). Input that doesn't match the SMS shape is returned untouched.

Migration `0005_normalize_sms_items` backfills existing rows. It only rewrites items that match the SMS format, saves every original to `ExpenseItemBackup` before touching it, and is idempotent — rows already backed up are skipped on re-run. `backwards` restores from those backups, so the migration is reversible.

Preview the impact before running it:

```bash
poetry run python manage.py preview_item_cleanup          # affected count + samples, no writes
poetry run python manage.py preview_item_cleanup --all    # print every affected row
```

## Auto-Classification

Expenses arriving from the webhook land as `UNSETTLED`. Rather than categorizing each one by hand, `auto_classify_service` learns deterministic rules from history and applies them.

A rule is adopted for a normalized merchant key only when all three hold:

1. Every past occurrence carries the **same** `(category, sub_category)` — an ambiguous merchant is skipped.
2. It appears at least `--min-count` times (default 2).
3. The key is at least 2 characters — one-character merchants are too ambiguous to trust.

The training set is **manually confirmed rows only** (`category != UNSETTLED AND auto_classified == False`). Rows the classifier itself wrote are excluded, so it can never learn from its own output. Only `UNSETTLED` rows are ever modified; classified rows are flagged `auto_classified=True`, which makes the whole operation reversible.

```bash
# Dry-run: report what would be classified, change nothing
poetry run python manage.py auto_classify_unsettled

# Require 3 confirmations before trusting a merchant
poetry run python manage.py auto_classify_unsettled --min-count 3

# Actually apply
poetry run python manage.py auto_classify_unsettled --apply

# Undo: reset every auto_classified row back to UNSETTLED (manual rows untouched)
poetry run python manage.py auto_classify_unsettled --revert
```

Unmatched `UNSETTLED` rows are reported in two buckets: **ambiguous** (the merchant has history, but it isn't deterministic enough to adopt) and **new** (never seen in confirmed history). The first tells you where the rules are too strict; the second is genuinely new spending.

## Testing

**134 tests across 14 modules**, run on a dedicated PostgreSQL test database.
(109 test functions; parametrized suites expand to 134 cases.)

| Module | Tests | What it covers |
|---|---|---|
| `receivers/tests/test_normalize_merchant.py` | 30 | Merchant normalization: `(일시불)` / `(할부N개월)` markers, date & time prefixes, corporate forms (`(주)`, `㈜`), idempotency, non-SMS passthrough |
| `expenses/tests/test_budget_viewset.py` | 20 | Budget CRUD, validation, duplicate guard, edge cases |
| `expenses/tests/test_auto_classify_service.py` | 21 | Rule learning (single-distribution / ambiguous / low-frequency / key-length boundaries), echo-chamber guard, dry-run vs apply, revert |
| `receivers/tests/test_parse_sms_service.py` | 13 | Shinhan & Woori SMS parsing, both formats, malformed input |
| `receivers/tests/test_card_payment_service.py` | 11 | `MM/DD` → date (year rollover, leap day, KST vs UTC), Notion and `Expense` get the same date, Notion failure saves nothing |
| `authentication/tests/test_auth.py` | 7 | JWT login / logout / token lifetime |
| `expenses/tests/test_preview_item_cleanup_command.py` | 6 | `preview_item_cleanup` command — reports impact, mutates nothing |
| `expenses/tests/test_auto_classify_unsettled_command.py` | 5 | `auto_classify_unsettled` command — dry-run default, `--apply`, `--revert` |
| `expenses/tests/test_normalize_sms_items_migration.py` | 5 | Data migration 0005 — forwards, backwards restore from backup, idempotency |
| `expenses/tests/test_expense_viewset.py` | 6 | Expense CRUD, read-only `auto_classified`, Notion import, multi-month summary |
| `receivers/tests/test_notion_migration.py` | 4 | Notion → DB import: duplicate skipping, batched `bulk_create` |
| `receivers/tests/test_sms_receiver_webhook.py` | 3 | SMS webhook → `Expense` flow with mocked Notion, unsupported card error |
| `expenses/tests/test_expense_summary.py` | 2 | Summary defaults (year/month, daily budget) follow the KST date |
| `config/test_health.py` | 1 | `/health/` endpoint |

The safety-critical paths get the most attention: anything that **writes** (the data migration, `--apply`, `--revert`) is tested for what it must *not* touch, not just what it changes.

External dependencies (Notion API) are isolated via `unittest.mock.patch`. Shared fixtures live in `conftest.py`:

- `user` — creates a test `User`
- `auth_client` — JWT-authenticated `APIClient`

```bash
# Run all tests
poetry run pytest

# With coverage
poetry run pytest --cov=.

# Specific app
poetry run pytest expenses/

# Re-run only failures
poetry run pytest --lf
```
